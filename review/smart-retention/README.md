# Smart retention review branch — no deployment
This isolated source branch is not the production branch. No migration, Storage API delete or cron schedule has been applied to live projects. Deployment requires separate user authorization.
## PTG / Data Desk
- The actual Product Master and SRP manual/workbook gateways use the new atomic dated catalog import RPC. Data Desk retains separate source-file effective dates. Missing barcode rows and blank fields are never removed, positive valid prices supersede older prices, and older/same-date conflicting sources cannot silently overwrite new information.
- System Admin must confirm the conservative upper bound for the effective dates of each existing legacy source before changing populated legacy values. The database does not guess these dates. The prior browser write grants and old SRP function execution are revoked by the coordinated migration candidate.
- Retention settings, holds, dry-run, manual eligible cleanup, source audit and widget notifications use existing validated System Admin sessions. Deletion is disabled in both database policy and runtime environment by default. Cleanup claims use a dedicated private registry and a fixed bucket; the worker verifies actual SHA-256 and size, revalidates the claim, calls the Storage API, and verifies absence before marking deletion. Uncertain results stay protected for review. No cleanup can target existing buckets.

## Release gates
- The current PTG import paths process original workbooks in browser memory and store extracted records, not original Storage objects. No unnecessary archive uploads are introduced; zero eligible originals is a legitimate result. The catalog registration RPC is for future intentionally retained originals and requires a committed import batch plus a verified unique immutable Storage object. No existing or unclassified files are enrolled.
- The 60-day rule applies only to registered source objects. Existing application asset buckets, projects, templates, product-photo library, editor bundles, and optional personal Drive backups must stay protected.
- All four repositories have project-local registry/worker candidates on the same review branch; central System Admin controls and notices use HMAC-authenticated server-to-server relay. Each target requires its own matching secret in the PTG gateway and target project (RETENTION_RELAY_SALES_SECRET, RETENTION_RELAY_MEGAFRAME_SECRET, RETENTION_RELAY_FLYER_SECRET in PTG; BRANCHLINE_RETENTION_RELAY_SECRET in the target). None are configured by this development branch. Each remote adapter deliberately has no source registration endpoint because current retained-source archives are not verified. It must remain empty unless a later trusted import adapter establishes durable import and dependency proof. Do not point the PTG service-role key at another project. Do not auto-clean browser-local projects or caches.
- Run the build-only review workflow. Real Storage API integration requires a disposable test bucket and object; mocked worker tests and synthetic database tests are not a substitute. Verify existing authenticated paths, browser UI and all project boundaries.
- For a later approved release, set a server-only RETENTION_CRON_TOKEN of at least 32 random characters and runtime flag RETENTION_RUNTIME_ENABLED=true only after verifying bucket and registry ownership. The scheduler must POST the internal worker with the secret header via a server-side Vault secret at 0 16 * * * UTC (midnight Philippine time). Do not enable the database release_authorized flag or schedule until separately approved. Never expose service credentials or the cron token to the browser.
- No cleanup activation, merge, or deployment authorized by this branch.
